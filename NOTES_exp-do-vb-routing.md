Phase 1 of the Vault Bubbles Data Orchard consumer code lives in `app/dataorchard/` (ids, capture with CaptureWriter, copy loaders plus synthetic scale, packed_tree adapter, lazy FastAPI router that is not mounted, and a NotImplementedError store seam), with tests in `tests/dataorchard/` (10 passing, no fastapi/DB needed). The real extension sends `{url,title,text,mode,tags,captured_at,pdf_to_parse,linked_pdf_urls}`, not `full_text/highlight/notes`; `normalize_payload` maps `text` to `full_text` for page mode, to `highlight` for selection mode (text after `[captured]`), and to `notes` for note mode. Nothing in app/main.py, models, db, migrations or extension was touched, and no database was contacted.

Phase 2 wires the package to orchard-db, orchard-cultivate and orchard-harvest: store.py (open-write-close per batch, make_write_batch upserts or, by default, calls insert_items so captures land in the tree at once, with the flag insert_on_capture and ttach), ngine.py (rebuild, ingest_new, hierarchy, find, recent over a cached read-only HarvestStore), scripts/dataorchard_build_copy.py (Forte copy or --pg-csv, optional --synthetic N --max-chars C --fake-encoder), and the success-bar suite (pp/dataorchard/bars.py, scripts/dataorchard_success_bars.py, 	ests/dataorchard/test_success_bars.py, 18 tests total with PYTHONPATH set to the three src dirs; the DB tests skip without them). Results are in exp/results/success_bars.json and success_bars.md. Databases used: exp/data/vb/forte.duckdb (279 docs, real MiniLM) and exp/data/vb/synth10k.duckdb (10,000 synthetic docs, real MiniLM with embedding max_chars capped to 512 so it builds in reasonable time); the shared exp/data/orchard.duckdb was never opened.

Headline results (details and caveats in exp/results/success_bars.md): packed_tree warm p50 about 35 ms at N=279 and 56-63 ms at N=10,000, cold about 70 ms and 600-670 ms (p95 under 0.75 s), HTTP /api/tree all-window warm 159 ms and cold 814 ms at 10k (6.8 MB payload); 500/500 captures saved with 0 field mismatches (421 unique items, all placed in the tree, 1 MB page included); known-item top-3 is 0.92 (title), 0.73/0.81 (mid-body sentence, hybrid/keyword), 1.0/0.99 (key terms); two-process A7 target of 0 reader failures was NOT met: the reader got 6 StoreBusyError in 24-12 requests because one writer batch holds the file lock for several seconds (longer than the 2 s reader retry), writer had 0 failures. Sources of this: insert_items holds the write connection through embedding and enrichment; a fix belongs in treedb/orchard (shorter lock, or readers serving the cached snapshot on StoreBusyError).
