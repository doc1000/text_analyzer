Graph Architecture Map

A visual systems map for the vault-aware graph/topic modeling subsystem. This diagram treats sparse graph state as the canonical relational layer, with hierarchies, clusters, layouts, and labels as derived artifacts. It is designed to help Opus generate the phased plan and help Cursor/Sonnet stay aligned during implementation.

Documents

Text, summaries, metadata, vault ownership, timestamps, existing embeddings, and future semantic enrichments.

Input: documents, summaries, embeddings

Vaults + Permissions

Vault membership controls graph visibility, mutation rights, bridge-edge rights, and rebuild scope.

Scope: owner / admin / editor / viewer

User Actions

Moves, must-link hints, category assertions, bridge approvals, layout nudges, and future feedback signals.

Role: affects immediate graph + future rebuild inputs

Feature Providers

Normalized access to embeddings now; later tags, categories, NER, classifier outputs, and user-intent signals.

Start small: embeddings + summary embeddings

Feature Fusion Engine

Builds ephemeral per-layer similarities/distances, applies weights, and produces candidate graph affinities.

Important: dense matrices are ephemeral, not persisted

Build / Update Jobs

Vault build, local insertion/deletion repair, bridge recompute, stale marking, and controlled rebuild operations.

Math lives here: Python/services

Vault Graphs

Persisted sparse internal edges per vault and graph version. This is the canonical relational state for the subsystem.

Examples: kNN graph, optional RNG-pruned graph

Bridge Edges

Cross-vault connections stored separately from internal edges. Rebuilt independently and governed by permissions.

Rule: do not rewrite protected internals

Graph Versions + Config

Vault graph metadata, build parameters, pruning mode, feature weights, and stale / active status.

Subgraph Extraction

SQL selects nodes and returns induced graph slices or composed graph slices without rebuilding the full corpus.

Default path: cheap, query-driven

Derived Hierarchy / Z

Optional linkage caches, local hierarchy payloads, semantic tree exports, and circle/group abstractions.

Derived only: never canonical

UI Payload Builders

D3 force payloads, grouped/circle payloads, composed multi-vault payloads, and optional local layout caches.

Frontend sees: nodes, edges, types, metadata

Labeling Module

Separate async system for topic/community labels and user overrides. Must not block graph rendering.

Canonical vs derived

Canonical documents vault memberships / permissions feature references sparse graph edges bridge edges graph versions / configs user structural actions Derived clusters topic groups Z arrays semantic trees layout coordinates group labels
Rule: do not let fixed clusters, tree nodes, or labels become the new source of truth.

Normal request flow

UI request ↓ SQL selects vault + permitted documents + requested subset ↓ SQL extracts induced graph slice and/or composed slice ↓ Python optionally derives local group/hierarchy payloads ↓ UI receives compact D3-ready payload ↓ labels attach if available (non-blocking)
Normal path goal: no full graph rebuild, no dense matrix regeneration, and no full-corpus transfer into Python.

Build / rebuild flow

documents + embeddings (+ future feature layers) ↓ feature providers ↓ feature fusion engine ↓ ephemeral similarities / distances ↓ sparse graph construction ↓ optional pruning (RNG / policy rules) ↓ persist graph edges + graph version ↓ mark derived caches fresh

Incremental update flow

new / updated / deleted document ↓ find local candidate neighbors ↓ recompute only local affinities ↓ insert / drop / repair sparse edges ↓ mark affected views stale ↓ leave full vault graph intact
Do not: re-derive the whole vault graph for ordinary insertions and deletions.

Multi-vault composition

vault A internal graph + vault B internal graph + stored bridge edges + optional ephemeral bridge candidates = composed view graph

The user experiences one graph in the UI, but persistence rules still distinguish internal edges from bridge edges.

Composition rules

  • Viewing multiple vaults together does not merge them canonically.
  • Bridge-edge recompute must not rewrite protected internal subgraphs.
  • Editors may change internal structure only within vaults they can edit.
  • Session-only view tweaks may exist without persisting edge changes.

Why keep feature scoring separate?

Graph core should own fusion and graph construction, but not block on every future enrichment pipeline. That allows embeddings/summaries first and tags/categories later.

Why keep labels separate?

Cluster labeling has different latency and interpretability tradeoffs. Separating it prevents LLM-generated labels from becoming a hard dependency for graph rendering.

What about existing tree artifacts?

Semantic trees and orchard/Z structures can remain as compatibility outputs or derived hierarchy caches while the sparse graph becomes the canonical relational layer.
